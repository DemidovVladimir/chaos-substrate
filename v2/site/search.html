Chunks, embeddings and search

A chunk is a passage of one section, at most 1200 characters. Each chunk is embedded once: the model turns it into a vector, a list of numbers that points at its meaning. Search ranks every vector against the question.

  • chunks of at most 1200 characters
  • 32 passages per embedding request
  • 120 s budget per request
  • 5 hits by default, every vector scanned
  • 心 model the embedding model and its vectors
  • data the index file
  • 印 hash ranking and content keys
  • 手 tools what the agent gets back

Cosine similarity measures how closely two vectors point the same way: 1 is the same direction, 0 is unrelated. Scores here are cosine similarities.

How blocks become chunks

Consecutive blocks under the same headings are packed while the result fits in 1200 characters, joined by a blank line (2 characters). A longer block is cut at whitespace into pieces of at most 1200 characters. Move the sliders; the block sizes are examples.

Sizes count the block's Markdown source, the text that is stored and embedded. A block with no letter or digit is skipped. A chunk's lines run from its first block to its last. A cut block gives about one piece per 1200 characters, because each cut falls at the last whitespace before the limit.

What the model sees

Prompt formats and the embedder id

Each chunk is sent with a context line: the note title, then its headings. A first heading that only repeats the title is left out, so Health/Allergies.md gives Allergies, not Allergies > Allergies. The wording shapes the vectors, so the format is part of the embedder id, the name of the vector space. The examples are the oil chunk of the example vault.

# a model whose name contains "embeddinggemma" in any letter case, e.g. the default
embedder id  embeddinggemma|gemma-retrieval-v1
passage      title: Car > Maintenance > Oil | text: I change the engine oil every 10 000 km.
query        task: search result | query: how often do I change the oil?

What sync embeds

Reused or embedded again

Each chunk has a content key: a hash of its context line and its text. A stored vector is reused when its key is unchanged and the index was built by the same embedder id.

  • reusenothing changedSame context, same text: the stored vector is kept.
  • embeda word or a format changedThe chunk text is the Markdown source, so even bold or punctuation gives a new key.
  • embeda note renamed or a heading changedThe context line changes, so the key changes.
  • oncetwo equal chunks in one syncEqual keys are sent to the model once, and both places are kept.
  • allanother model or formatThe embedder id differs, so no stored vector is reused.
  • dropa chunk deletedIts vector is removed in the same write.
Enforced in code

Guarantees

  • Exact ranking. Every stored vector is compared; nothing is approximated or sampled.
  • Deterministic order. Best score first; equal scores keep the earlier passage first.
  • One vector space. A stored vector of another length is refused, and so is an index built by another embedder id.
  • The reply is checked. One vector per input, indexes 0 to n-1, none empty, all one length; anything else fails the sync.
  • No empty requests. When nothing needs embedding, the model is not called.
  • The key stays out of errors. A failed reply is quoted to at most 200 characters, with the API key replaced by [redacted].
  • Chunk rows are verified. A stored chunk that does not hash to its key is an error, not a result.
  • The API key travels only where nobody else reads it. It is sent over https://, or over plain http:// only to localhost, 127.0.0.0/8 or ::1; otherwise the request is refused before it is made.
  • Local text stays local. Proxy settings from the environment are used for remote embedders only, never for this machine.
