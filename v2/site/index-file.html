The index file

The index is one redb file, by default <vault>/.chaos-kb/index.redb. It holds the note hashes, the chunks, their vectors and the block fingerprints. A sync rewrites it in one transaction. Delete it, and the next sync rebuilds it.

  • 5 tables in 1 file
  • 1 write transaction per sync
  • layout mark format = "2" in meta
  • up to 3 attempts when another writer wins

One write, step by step

How a sync replaces the index

redb is an embedded database written in Rust: one file, no server. A transaction is a group of changes that is saved all at once or not at all. A lock file is an empty file that one process at a time may hold.

What is inside

Five tables

One row of each table, from the example vault. chunks and blocks are multimaps: one key can hold several rows.

A chunk's key comes from its context line and text only. Two notes with the same title, section and words, such as x/Plan.md and y/Plan.md, share one key and one vector, and chunks keeps a row for each, so a search and a same-words check both name both notes. The tree table keeps the name it had when chaos-kb also hashed every note into one root, so index files written then still open; it holds only the note hashes.

Try it: two writers

When another sync gets in first

A sync reads the index, embeds what is new, then writes. Say another process, such as a running MCP server, writes in between. Pick how often that happens to one sync; the rule is SYNC_ATTEMPTS in src/application/sync.rs.

    Each attempt starts from the index as it is then, so the work of the other writer is kept and only what is still missing is embedded. remember and forget each run two syncs, and each sync has its own attempts.

    Outcomes

    What the file can be

    • noneno file yetReads find nothing and create nothing; check and search say to run sync.
    • nonean empty fileRead as no file, until a sync fills it.
    • noneanother layoutA file without format 2 in meta, from an older or newer build, reads as empty. The next sync clears it and rebuilds it.
    • waitheld by another processEvery operation waits for <index>.lock, as long as it takes.
    • againanother writer got in firstThe write is refused and the sync starts over: at most 3 attempts, then the index changed while this sync ran.
    • refusea chunk without a vectorThe write stops and the index is unchanged.
    • refusea query of another lengthThe stored vector's length is named, with a hint about the embedder.
    • errora row that does not decodeAn error, never a crash or a wrong answer.
    Enforced in code

    Guarantees

    • Derived and disposable. The notes are the knowledge. Delete the file and the next sync rebuilds it with the same note hashes.
    • All or nothing. A sync writes in one transaction, so the file holds the old index or the new one.
    • A late sync never overwrites a newer index. The write goes through only while the index still holds the snapshot that sync started from.
    • Shared, one at a time. The CLI, a running MCP server and the dashboard each hold <index>.lock for the length of one operation.
    • No orphans. A vector that no chunk uses is dropped in the same write.
    • Every place is kept. The same passage or block in several notes keeps a row for each.
    • Nothing trusted on read. A file of another layout reads as empty; a stored note path must be valid, a chunk row must hash to its key, and a vector must be whole 4-byte numbers.
    • One vector space per file. meta records the embedder id, and reads by meaning with another id are refused.
    Try it

    Old file, held file, no file

    On copies of the example vault; the first holds an index file written by an earlier chaos-kb build, without the layout mark. JSON is shown condensed. The file size is an example; for a vault of 503 notes the index was 8.4 MB (README § Speed).

    $ chaos-kb check "allergic to penicillin"
error: the index is empty: run `chaos-kb sync` first
$ chaos-kb sync
{ "added": ["Car.md", "Communication.md", "Health/Allergies.md"], "notes": 3, "chunks": 5, "embedded": 5 }
# another process holds .chaos-kb/index.redb.lock for 2 s; this check starts 0.3 s in
$ chaos-kb check "allergic to PENICILLIN"
{ "known": true, "presence": "exact", "matches": [ { "note": "Health/Allergies.md", "section": "Allergies", "lines": [3, 3] } ], ... }
# answered after 1.7 s: it waited for the lock
# a copy after the edits of the Fingerprints page
$ wc -c .chaos-kb/index.redb
  118784 .chaos-kb/index.redb
$ rm -r .chaos-kb && chaos-kb sync
{ "added": ["Car.md", "Talking.md"], "notes": 2, "chunks": 4, "embedded": 4 }
# every chunk embedded again: the vectors were only in the deleted file
$ chaos-kb check "x" --index ./none.redb
error: the index is empty: run `chaos-kb sync` first

    Use --index or CHAOS_KB_INDEX to keep the file somewhere else; its lock file sits next to it. A missing file is not created by a read.
