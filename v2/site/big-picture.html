From notes to answers

You keep what you know as Markdown notes in one folder. One sync turns them into fingerprints and searchable passages in one index file. Then an agent can ask: is this known, and what do my notes say?

A note becomes an answer

The seven tools

Three write, four read

The same seven tools exist as commands (chaos-kb sync) and as MCP tools for agents (kb_sync). Every command prints JSON.

sync

Makes the index match the vault. Compares note hashes, embeds only new or edited chunks, and drops deleted ones. Run it after you edit notes. Fingerprints

remember

Stores one fact in a note and indexes it. It syncs first, and skips the fact when the same words are already anywhere in the vault. The vault

forget

Takes a fact out of the notes and the index: every block with the same words, in every note or in one. It syncs before and after, and never removes a passage that only means the same. Taking a fact out

check

Is this already known? Same words are found from the fingerprints, with no model call. Otherwise the three nearest passages decide. How check decides

search

The passages most similar to a question, best first, with note, section, line range and text. Five by default. Search

topics

What the notes hold near a task: one short line per passage (id, section, score, first words), best first, no text. Eight by default. Topics and read

read

The passages behind ids from topics, with their text, in the order asked. No model call. Topics and read

How the code is split

Five layers, one rule each

A port is a trait: what a use-case needs from outside. An adapter implements one. The layering test in src/lib.rs fails when a file names a layer it may not use.

domainPure rules: text, hashes, what changed, chunks, vectors, paths, presence.uses nothing in the crate
portsVault, Embedder, Index, and the shapes they pass.uses domain
applicationThe seven use-cases on Kb, plus the dashboard's overview: one vault, one index, one embedder.uses domain, ports
adaptersThe Obsidian vault on disk, the redb index file, the HTTP embedder.never application or entry
entryThe clap command line, the MCP server, the dashboard and the tool roster they share.wires adapters in

What a sync reports

Seven situations

A sync report holds the counts notes, chunks and embedded, the notes added, changed and removed, and dry_run.

  • newfirst syncEvery note is added and every chunk is embedded.
  • samenothing changedembedded is 0 and the three note lists are empty.
  • edita note editedchanged lists it; only its new chunks are embedded.
  • gonea note deletedremoved lists it; its vectors, chunks and fingerprints are dropped.
  • modelanother modelOld vectors are never reused, so every chunk is embedded again.
  • lookdry runThe counts only. Nothing is embedded or written.
  • againanother writer got in firstThe sync starts over from the index as it is then, at most 3 attempts in all.
Enforced in code

Guarantees

  • The vault is the only copy. The index is derived from the notes and is rebuilt by the next sync when you delete it.
  • No fake vectors at run time. The test doubles (an in-memory vault and index, a keyword embedder) live in src/application/testing.rs, compiled only for tests.
  • A failed embedding writes nothing. When the model fails, returns the wrong number of vectors or a zero vector, sync stops before the index changes.
  • One vector space at a time. Stored vectors are reused only when the index was built by the same embedder id: model plus prompt format.
  • Reads need an index. check and search refuse an empty one and say to run chaos-kb sync. Comparing vectors also needs the configured embedder's index; the same words answer without it.
  • Processes take turns. Index operations hold <index>.lock, and appends and removals hold .chaos-kb/append.lock, so a CLI command, a running MCP server and the dashboard can share one vault.
  • Blank input is refused. A query or fact with no letter or digit is an error, not a lookup.
  • Layers stay apart. The layering test keeps the domain pure and keeps adapters out of the use-cases.
Measured, not promised

How fast it is

Measured on an Apple M4 with the release build, Ollama 0.24 and embeddinggemma, on a vault of 503 notes (1004 chunks). Each time covers the whole process run (README § Speed). The first sync, which embeds all 1004 chunks, took 12.6 s. The index file was 8.4 MB.

check, by meaning0.14 s
sync, one edit0.14 s
sync, unchanged0.09 s
search0.09 s
check, same words0.04 s

The check by meaning and the sync after editing one note each make one embedding call. The check by the same words makes none.

Try it

Install, sync, sync again

Needs Rust 1.91 or later and Ollama with the embedding model. The output below is from an example vault of three notes: Car.md, Communication.md and Health/Allergies.md. JSON is shown condensed.

$ ollama pull embeddinggemma
$ cargo install --path v2
$ export CHAOS_KB_VAULT=~/Knowledge
$ chaos-kb sync --dry-run
{ "added": ["Car.md", "Communication.md", "Health/Allergies.md"], "changed": [], "removed": [],
  "notes": 3, "chunks": 5, "embedded": 5, "dry_run": true }
$ chaos-kb sync
{ "added": ["Car.md", "Communication.md", "Health/Allergies.md"], "changed": [], "removed": [],
  "notes": 3, "chunks": 5, "embedded": 5, "dry_run": false }
$ chaos-kb sync
{ "added": [], "changed": [], "removed": [], "notes": 3, "chunks": 5, "embedded": 0, "dry_run": false }
$ chaos-kb check "allergic to PENICILLIN"
{ "known": true, "presence": "exact", "matches": [ { "note": "Health/Allergies.md", "section": "Allergies", "lines": [3, 3] } ] }
# without a vault: error: set --vault or CHAOS_KB_VAULT
